TITLE: How GPUs Actually Work: Grids, Blocks, & Cores Explained

DESCRIPTION:
Welcome to the foundational video in our GPU programming series! In this comprehensive deep dive, we explore the big picture of how a GPU executes work, bridging the gap between the software code you write and the physical hardware that runs it. 

At a high level, a GPU is a specialized chip that contains many identical processing blocks known as Streaming Multiprocessors, or SMs. You can think of each SM as a small, highly parallel CPU cluster that is capable of running thousands of lightweight threads simultaneously. When you launch a GPU kernel—which is simply a function designed to run on the GPU—you do not manually assign individual threads to specific SMs or partitions. Instead, you tell the system the exact number of blocks and the number of threads per block you want to utilize. The GPU runtime and the underlying hardware take over from there, distributing these blocks across the available SMs. Inside each SM, the hardware automatically splits the threads into groups of 32, which are called warps. Each warp is then assigned to a specific SM partition, where a dedicated warp scheduler issues instructions to the underlying execution units, such as CUDA cores or tensor cores. 

Understanding this system requires grasping two distinct but connected hierarchies: the programming view and the hardware view. From the software perspective, you deal with a Grid, which contains Blocks, which in turn contain Threads. The Thread is the absolute smallest unit of execution in your kernel, typically running your kernel function on a single element, such as one pixel or one array index. A Block, or thread block, is a grouping of these threads that all run on the very same SM. Because they share the same SM, threads within a block can share fast on-chip shared memory and can synchronize their execution using commands like `__syncthreads()`. The Grid represents all the blocks that are launched for a single kernel call. Internally, the hardware groups 32 consecutive threads from a block into a Warp, which is the true hardware execution unit where all threads execute the exact same instruction in lockstep, a paradigm known as SIMT (Single Instruction, Multiple Threads). A single kernel launch maps each block entirely to one SM, though one SM can host many blocks simultaneously depending on its available resources.

On the physical hardware side, the architecture moves from the GPU chip down to the SMs, then to SM partitions, and finally to the cores. A single GPU chip contains many SMs (in NVIDIA terminology) or CUs (in AMD terminology). Each SM functions as a "mini-GPU factory," possessing its own register file, shared memory, warp schedulers, and a pool of execution units like CUDA cores, tensor cores, and special function units. Modern SMs, such as those in NVIDIA Ampere, Hopper, or H100 architectures, are internally divided into multiple partitions or sub-partitions. Warps assigned to an SM are distributed across these partitions, and each partition operates with its own warp scheduler, dispatch units, and a dedicated slice of execution cores. You never program these partitions explicitly; they are micro-architectural details utilized by the hardware to maximize parallel efficiency. Inside these partitions, physical execution occurs on CUDA cores for basic integer and floating-point math, Tensor cores for matrix-multiply ML workloads, and Special Function Units (SFUs) for complex operations like sine or cosine. 

To make this concrete, consider a step-by-step vector addition kernel. If we launch a kernel to add 1,000,000 elements using 256 threads per block, we define a grid of approximately 3907 blocks. Within each block, the 256 threads are divided into 8 warps. The driver enqueues this launch, and the GPU hardware pulls from a global pool of blocks, assigning them to SMs as room becomes available. A block will stay on its assigned SM for its entire lifetime. Inside the SM, the warps are registered to one of the SM's partitions. The warp scheduler in that partition will repeatedly pick a ready warp—one not stalling on memory or synchronization—and issue its next instruction to the cores. If one warp stalls to wait for a memory load, the scheduler seamlessly interleaves another ready warp to hide the latency. 

By remembering that you write grids, blocks, and threads, but the hardware executes SMs, partitions, warps, and cores, you will be equipped to reason deeply about GPU performance and execution behaviors.

TITLE: Single GPU Programming: Understand Warps & Threads

DESCRIPTION:
In this video, we strictly define the core concepts of the CUDA programming model for a single GPU scenario, thoroughly unpacking how grids, blocks, threads, and warps operate and directly translate to hardware components. 

When launching a kernel in CUDA, the programmer must specify an execution configuration, which intrinsically defines a "grid" composed of "blocks", where each block contains multiple "threads". The Thread is the fundamental, smallest unit of execution. Each thread is responsible for running the kernel code on one specific piece of data, such as a single array element, and is identified by indices like `threadIdx.x`. A Block, or thread block, is a cooperative group of these threads. Crucially, all threads within a single block are guaranteed to run on the exact same Streaming Multiprocessor (SM). This physical proximity allows them to synchronize their execution using barriers like `__syncthreads()` and cooperate efficiently by passing data through incredibly fast on-chip shared memory. Threads inside a block are automatically grouped by the hardware into sets of 32, known as a Warp. The warp is the actual unit that the SM's warp scheduler issues to the hardware cores to execute in lockstep via the SIMT (Single Instruction, Multiple Threads) model. Finally, the Grid is defined as the full, complete collection of thread blocks that are launched by a single kernel call. Every time you launch a kernel, you are creating exactly one grid. This grid acts as an ordered set of blocks, and while different grids can theoretically be active concurrently on a GPU through the use of streams, a single grid always maps to a single kernel function's wave of work.

Understanding how this software grid maps to the physical GPU hardware is vital for performance. On the hardware side, the GPU contains multiple Streaming Multiprocessors. When your code generates a grid of blocks, the GPU runtime assumes the responsibility of scheduling those blocks across the available SMs. A single SM can, and usually does, run multiple blocks simultaneously, up to specific hardware limits such as the maximum allowed blocks per SM or maximum threads per SM. As a programmer, you do not directly assign blocks to specific SMs; this distribution is handled entirely by the hardware. Once a block resides inside an SM, it is split into its constituent warps of 32 threads, which are then stored in the SM's scheduler queues. Every clock cycle, the warp scheduler within an SM partition selects a ready warp and dispatches its instruction into the core execution pipelines. 

Let's look at a practical 1D vector addition example. If we are adding vectors of one million elements, we might launch a grid consisting of 3907 one-dimensional blocks, with each individual block containing exactly 256 threads. Within each block, those 256 threads naturally divide into 8 distinct warps (256 divided by 32). On the physical GPU, these 3907 blocks are distributed across the chip's SMs. Each SM will hold a subset of those blocks concurrently. Inside any given SM, all the threads belonging to its resident blocks are continually scheduled as warps and executed directly on the SM’s cores. 

To summarize your mental model: a grid represents the entire wave of work for one kernel launch. This grid is constructed of blocks, which are teams of cooperating threads. The GPU hardware executes these blocks on its SMs, and inside each SM, the threads are executed in 32-thread groups called warps. Mastering this single-GPU programming model is the first step toward effective performance tuning, as you must choose grid and block sizes that fully utilize the SM resources and ensure excellent memory access patterns.

TITLE: Multi-GPU Scaling: Data Parallelism Explained

DESCRIPTION:
Once you have mastered the single-GPU execution model, the next major milestone is understanding how work is split across multiple GPU devices simultaneously. In this video, we dive deep into the multi-GPU programming model, assuming you are already familiar with grids, blocks, threads, and warps. 

When utilizing multiple GPUs, the most prevalent and effective strategy is Data Parallelism. In a data-parallel setup, every single GPU runs the exact same kernel, meaning they all use the same overarching grid configuration logic. The core difference is that the massive global input data is partitioned into disjoint chunks, or batches, and distributed. Each GPU processes its own isolated chunk completely independently of the others. Afterward, the individual results are gathered and combined on the host CPU, or through collective communication operations if you are running complex distributed training workloads. Inside each individual GPU, the standard single-GPU story perfectly applies: the blocks of its specific grid are scheduled onto that particular device's Streaming Multiprocessors (SMs). 

A highly common practical pattern for writing single-process, multi-GPU CUDA C/C++ code involves a clear sequence of steps. First, the program queries the system for the total number of available devices. Second, it decides the mathematical logic for how to split the global batch of data. Third, a single CPU host process uses a loop to iterate over the devices, setting the active device, and launching the same kernel on each one. Finally, the host synchronizes and gathers the computed results. 

To visualize how grids look across devices, let's use a vector addition example with 1,000,000 elements distributed across 2 GPUs. We might assign 500,000 elements to each GPU and use a block size of 256 threads. On GPU 0, it processes the data slice from index 0 to 499,999. This requires a grid of approximately 1954 blocks, so we launch the kernel with that grid size specifically on GPU 0. Simultaneously, GPU 1 processes the data slice from index 500,000 to 999,999. We launch the exact same kernel configuration—1954 blocks of 256 threads—on GPU 1, but we pass it pointers that direct it to its specific slice of the memory. The vital takeaway here is that each GPU possesses its own completely independent grid. From the developer's perspective, you are just launching the same kernel many times—once per device—with differing data pointers. 

Batching these data chunks can be handled in a few ways. The simplest is equal-size data batches, where the global batch is simply divided by the number of GPUs. This is ideal for homogeneous setups where all GPUs are the exact same model. However, if you have differing GPUs (like pairing a massive A100 with a smaller GPU), you might need load-balanced or performance-aware batching, assigning larger data chunks to the faster hardware, or using a dynamic work queue where each GPU pulls new mini-batches as it finishes previous ones. Even inside a single GPU, breaking its local slice into smaller mini-batches can help overlap data transfers with computation, reducing peak memory requirements. 

Moving data involves host-device transfers per GPU. Typically, you set the device (`cudaSetDevice`), allocate memory on that specific device, copy the slice of data from the host to that device, launch the kernels, and copy the results back. By utilizing CUDA Streams, you can make these memory transfers asynchronous, overlapping the copying of data with the execution of compute kernels to maximize throughput. While basic data parallelism doesn't require GPUs to talk to one another during the compute phase, advanced workloads might use Peer-to-Peer (P2P) memory copies (`cudaMemcpyPeer`) or deep learning communication libraries (like NCCL) to synchronize data directly across devices. 

In practice, there are two dominant multi-GPU architectural patterns. The first is using one host thread or process to control all GPUs via a single main loop. This is simpler to implement and highly effective when the work assigned to each GPU is very large. The second pattern is utilizing one process or thread per GPU. This is incredibly popular in MPI frameworks or distributed ML training setups, where each process is rigidly bound to a specific device and the input data is partitioned across processes ahead of time. 

Multi-GPU programming is fundamentally layered. Inside one device, you focus on grids, blocks, threads, warps, and single-chip memory hierarchies. Across devices, you focus on splitting data, launching multiple grids, and coordinating data transfers. By keeping these two conceptual layers strictly separate, it becomes incredibly straightforward to scale a high-performance single-GPU kernel out to a massive multi-device cluster while reusing the exact same kernel code.

TITLE: Maximize GPU Performance: Master the Tuning Knobs

DESCRIPTION:
Welcome to your beginner-friendly guide to mastering GPU performance tuning! In this video, we focus on the three most critical performance tuning knobs available to programmers—Block Size, Occupancy, and Warp Divergence—and explicitly tie them back to the underlying physical GPU hardware hierarchy of SMs, partitions, warps, and cores. 

The first massive knob you control is the Block Size, which is simply the total number of threads assigned to a single block. Common configurations include 64, 128, 256, 512, or 1024 threads per block, with 1024 typically acting as the hard CUDA maximum. Because an entire block runs on a single SM and is internally split into warps of 32 threads, a block size of 256 threads will result in exactly 8 warps per block. Block size is crucial because it heavily dictates your Occupancy, determines how many hardware resources (like registers and shared memory) are consumed per block, and affects scheduling flexibility. If you choose blocks that are too small, the SM might hit its hard limit for "max blocks per SM" while still having very few active warps, bottlenecking performance. Conversely, massive blocks mean fewer blocks can physically fit on the SM, leaving the scheduler with fewer options to hide latency if one block stalls. A great practical starting rule is to default to 128 or 256 threads per block, as these sizes frequently provide excellent occupancy and high scheduling flexibility. By choosing a block size, you are indirectly deciding how many warps each SM partition's scheduler will have available to hide latency. 

Our second tuning knob is Occupancy. In CUDA terminology, occupancy is the ratio of active warps currently running on an SM to the theoretical maximum number of warps that SM hardware can support. For example, if the hardware supports 64 max warps per SM, and your configuration results in 32 active warps, your achieved occupancy is 50%. Occupancy is vital because GPUs hide memory and instruction latency by rapidly switching between warps. If one warp stalls while waiting for global memory, the warp scheduler instantly picks another ready warp from its queue. Higher occupancy provides more warps to choose from, increasing the likelihood that the hardware always has something ready to run, thereby maximizing core utilization. However, it is a critical rule that higher occupancy is not the ultimate goal; higher performance is. Factors that restrict occupancy include your chosen block size, the number of registers required per thread, shared memory usage per block, and hard hardware limits. Tools like Nsight Compute will explicitly tell you which of these factors is currently limiting your occupancy. When occupancy is high, every SM partition is more likely to have multiple ready warps, keeping all physical cores furiously busy. 

The third knob is Warp Divergence. Warp divergence occurs when threads that belong to the exact same warp take diverging control-flow paths—such as an `if/else` statement. Because a warp is fundamentally designed to execute one common instruction at a time across all 32 threads, divergence forces the warp to serialize execution. If half the threads evaluate an `if` condition as true and the other half evaluate it as false, the warp must run the `if` path while masking off the inactive threads, and then run the `else` path while masking off the previously active threads. This destroys your SIMT (Single Instruction, Multiple Threads) efficiency. The warp scheduler still issues one instruction per cycle, but significantly fewer thread lanes are actually doing useful arithmetic work, causing your cores to be severely underutilized. Typical sources of this performance killer include data-dependent `if` conditions, loops with varying iteration counts per thread, and early function exits. To fix it, engineers should strive to make branch conditions uniform across a whole warp, or refactor algorithms to remove complex branching from the hottest execution paths. 

As a bonus tuning knob directly tied to warps, we also must discuss Memory Access Patterns. Coalesced access occurs when all threads in a warp access contiguous, aligned memory addresses. This allows the hardware to fulfill the memory request with minimal transactions. Uncoalesced access occurs when threads request scattered memory addresses, resulting in multiple costly memory transactions. Poor coalescing puts immense pressure on the memory bandwidth, forcing the warp schedulers to rely entirely on incredibly high occupancy to hide the resulting massive memory latency. Prioritize Structure of Arrays (SoA) data layouts over Array of Structures (AoS) to naturally encourage coalesced memory accesses. 

By understanding how block size shapes warp creation, how occupancy fuels the warp schedulers, how divergence wastes core cycles, and how coalescing saves memory bandwidth, you can read any profiler report and directly tune the underlying hardware.

TITLE: GPU Hardware Limits: Stop Trusting Spec Sheets Alone

DESCRIPTION:
Welcome to a deep dive into the physical constraints of GPU architecture! In this video, we break away from theoretical marketing numbers and explore exactly how hard system limits—such as max warps per SM, max threads per SM, register file sizes, and shared memory limits—strictly constrain and shape the parallelization you can actually achieve. We will be using the hardware specifications of the Tesla P100, V100, and A100 GPUs to demonstrate how these boundaries dictate your code's performance. 

Every Streaming Multiprocessor (SM) has strict upper bounds. For the P100, V100, and A100 architectures, the hardware dictates limits of 32 threads per warp, a maximum of 64 warps per SM, 2048 maximum threads per SM, 32 maximum blocks per SM, 65536 32-bit registers per SM, and a hard cap of 1024 threads per single block. Shared memory per SM varies by generation: the P100 provides 64 KB, the V100 provides configurable memory up to 96 KB, and the A100 provides configurable memory up to 164 KB per SM. Your kernel’s unique execution configuration determines how closely you approach these theoretical bounds. 

Let's examine how these limits constrain your Occupancy. With 32 threads per warp and 64 max warps, the theoretical maximum number of active threads per SM perfectly equals 2048. Suppose you launch a kernel with 256 threads per block, requiring 64 registers per thread and 16 KB of shared memory per block. The thread capacity limit allows for 8 blocks per SM (2048 / 256). Those 8 blocks contain exactly 64 warps, hitting the hardware warp limit exactly. Because 8 blocks is well under the 32 max blocks per SM limit, this configuration mathematically allows for 100% theoretical occupancy. 

However, in the real world, the Register Limits drastically alter this picture. The SM contains exactly 65536 registers. If your kernel is highly complex and the compiler allocates 128 registers per thread, a block of 256 threads will demand 32,768 registers. Because the SM only has 65536 registers available, it can physically only host 2 blocks at a time (65536 / 32768). Therefore, even though the thread and warp limits could theoretically support 8 blocks, the register file exhaustion forces the SM to hold only 2 blocks. This drops your active threads to 512 and active warps to 16, instantly plummeting your achieved occupancy to just 25%. High register usage brutally reduces the number of warps in flight, robbing the SM partitions of their ability to hide latency. 

Shared Memory limits enforce similar boundaries. If you are utilizing an A100 GPU (which has 164 KB of shared memory per SM) and your block requires 48 KB of shared memory for a large data tile, the SM can only fit 3 blocks at a time (164 KB / 48 KB). This results in only 768 active threads and 24 active warps per SM. Even on the mighty A100, shared memory exhaustion restricts you to a fraction of the theoretical 64 warps, significantly hurting the scheduler's ability to hide memory stalls. Programmers must carefully balance the size of their shared memory tiles against the resulting drop in concurrent resident blocks. 

Furthermore, the hard limits on Block Counts must be navigated. The absolute maximum block size is 1024 threads. If you attempt to launch blocks with only 32 threads (a single warp), the maximum blocks per SM limit of 32 kicks in. You would only achieve 32 active warps on the SM—exactly 50% of the maximum—simply because the hardware ran out of block slots before it ran out of thread capacity. This is why extremely tiny block sizes are discouraged; a sweet spot of 128 to 256 threads usually ensures you are limited by warps or registers, rather than wasting potential parallelism on block count limits. 

Comparing the P100, V100, and A100 reveals how hardware evolution shapes tuning. Many base limits remained identical across these generations, but the massive expansion of shared memory on the A100 (up to 164 KB vs the P100's 64 KB) represents a huge architectural shift. A kernel that requires heavy shared memory tiling might be severely crippled by low occupancy on the P100, but that exact same kernel could achieve incredibly high occupancy on the A100, giving developers far more flexibility in their tuning tradeoffs. 

When writing and tuning your code, you must actively navigate these ceilings. Pick a block size that is a multiple of 32, estimate your occupancy against the 2048 thread and 64 warp limits, and then rigorously check if your register or shared memory usage is prematurely bottlenecking your parallelism. Remember to evaluate GPUs holistically; the numbers on the spec sheet are just the ceiling, but your kernel’s actual resource usage dictates how much parallel performance you will actually realize.
